# Zod parsed-output evidence

A permissive request schema and an unsafe write are different claims. A default
Zod object may accept a request containing unknown keys while removing those
keys from its parsed output. Treating the absence of `.strict()` as proof of
mass assignment confuses these two boundaries.

## Scope of the change

The scanner now records a bounded chain from the submitted archive:

- The nearest package manifest and lock identify the supported declared Zod
  version **3.25.76**, with no unresolved dependency alias, incompatible range,
  nested Zod dependency or TypeScript/JavaScript module remapping.
- A direct runtime `import { z } from 'zod'` defines an explicit, recursively
  closed object shape. Its scalar refinements and declared nested objects are
  supported. Passthrough/catchall, records, unknown/any, transforms, preprocessors,
  composition, schema mutation and unresolved aliases are not treated as strip.
- A local `parse`/`safeParse` result, or an explicitly resolved helper that
  returns its guarded `safeParse` result's `data`, feeds a recorded write payload.
- The scanner links direct immutable projections/destructuring and a bounded
  `let` assignment inside a try with a terminal catch. Raw request aliases,
  computed request access, spreads in a checked payload, mutations and aggregate
  escapes remain unknown.

The supported dependency behavior is grounded in
[Zod 3.25.76 object construction](https://github.com/colinhacks/zod/blob/v3.25.76/packages/zod/src/v3/types.ts#L2880-L2894):
ordinary object creation uses `unknownKeys: strip` and `ZodNever` as its catchall.
Other versions and import APIs are intentionally unsupported by this first
bounded verifier. The lock is a declaration of the dependency contract, not a
claim to have inspected the server's installed package or executed a parser.

Source file hashes, the lockfile hash, schema location, parsed binding and write
locations are recorded. No source literals are copied into this evidence.
Reading, parsing and package/module traversal have explicit budgets. The scanner
does not execute submitted JavaScript or call a model for this check.

## Disposition and report behavior

Evidence is generated by `SyntaxVerifier` from archive bytes. Model JSON may
request a review through its narrative, but supplied check results, aliases or
nested proof objects are never trusted.

The check establishes the **static argument passed to the recorded write call**.
It does not prove the implementation of an arbitrary method named `update`,
`insert` or `upsert`, database behavior, downstream transformations, runtime
monkeypatching outside the bounded source inventory, or whole-program safety.

A complete whole-finding contradiction is allowed only for a narrow statement
that unknown input keys reach the cited **write payload**, with a matching
atomic narrative and coordinates inside the single recorded write. The original
finding remains stored and visible; the existing scoring policy excludes its
contradicted premise from penalties.

An assertion about unknown keys being stored has only partial counterevidence
when this chain shows a stripped payload. Other claims, including a contractual
requirement to reject input, remain unresolved. Its original severity stays in
the score under the existing partial-evidence policy.

A finding that correctly says unknown input is accepted and ignored receives
observed parsed-output context, not a false contradiction. Negated or conditional
storage statements do not create positive storage claims. The report displays
that accepting a request and removing keys differs from rejecting the request,
plus the checked parse and write locations. No finding text is rewritten or
silently deleted.

## Verification

The synthetic suite covers safe same-file parse/safeParse flows, imported helper
and schema flows, nested fields, try/catch and destructuring; it pairs those with
open schemas, false guards, raw-body/spread/alias/mutation bypasses, helper
shadowing/reassignment, namespace/barrel consumers, remapped or malformed
manifests, source mutations of the shared Zod contract, compound/negated claims,
wrong write coordinates and forged model evidence. A fake-model pipeline case
checks retained text, evidence disposition and rendered report text.

Targeted gate: **211 passed**, including **87 new synthetic tests**, with no
external model service:

```bash
python -m pytest \
  tests/test_zod_write_evidence.py \
  tests/test_atomic_claims.py \
  tests/test_atomic_claims_v5.py \
  tests/test_claim_evidence.py \
  tests/test_engine_version_pins_the_scanners.py -q
```

A private local replay used the accepted observations and pinned source from the
previous production audit. Provider response bodies were unavailable, so source
quotes and citation end positions were reconstructed; this is not a byte-for-byte
provider-response replay. The private report and customer source were not added
to the public repository.

For the five reviewed Zod observations, two receive partial storage
counterevidence and three receive observed parsed-output context. None is marked
as a whole-finding contradiction: their titles state that input is not rejected,
which is true for the supported default-strip schemas. The retained Free count
and total remain **12 / 8.8**; the standalone Pro replay remains **49 / 5.0**.
All accepted observations are retained. These results are intentionally not a
score-improvement claim for the Zod check.

This PR is based on the React observation-identity change in PR #458. The
combined targeted gate passed **309 tests** and repository-wide Ruff passed.
Its integrated replay retains the React result: Pro **45 / 5.1**, Frontend
**5.1**, Free **12 / 8.8**. All 59 Pro originals and all 12 Free originals retain
their substantive fields and provenance; grouping remains idempotent. The
historical Free baseline snapshot and complete rendered baseline HTML remain
unchanged. Two Free observations receive partial counterevidence and three
receive observed context, with no whole-finding contradiction.

The engine version changes to `2026-09-09-2` because new audits contain additional
source evidence and report qualification. Historical Free baselines are not
retroactively rewritten.
